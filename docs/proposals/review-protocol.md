# PR 评审协议（proposal）

> 状态：draft。本文是孵化稿，规则真源仍是 AGENTS.md 与 ADR-0007；毕业后再迁入正式层。

## 背景

### 触发事件：PR #13 的三轮评审

| 轮次 | 发现 | 修正 | 代价 |
| --- | --- | --- | --- |
| 1 | 3 阻塞 + 3 非阻塞：取代链方向写反、git-workflow 前置失实、补录 PR 数少算、`经 journal 记账`无先例、SPEC-0007 虚构编号、80 行重写表述失实 | amend + force push | 一次全量 CI |
| 2 | 修正引入新问题：A9 来源账伪先例、时区 `Z` / CST 混用 | amend + force push | 一次全量 CI |
| 3 | PR 标题仍是「重写」、描述中的评审记录仍是旧版 | 仅改平台元数据 | 一次人工复核 |

三轮的共同点：**每一轮都只发现了上一轮视野内的东西**。内容错误、修正引入的回归、平台元数据，本可以在一次完整检查里全部暴露。

### 根因

1. **没有固定清单**：评审靠临场发挥，先看到什么报什么；PR 标题/描述没有被当作「落地物」检查。
2. **没有回归检查**：第二轮只验旧 ID，没验修正引入的新表述，于是修一处、坏一处。
3. **评论是散文**：没有 ID、状态、证据，作者不知道哪条关了、哪条还开着，只能靠人记。
4. **角色与授权未定**：作者改还是评审者改、force push 谁批、合并谁点，每次都要人类转达。

### 现有约束

- **ADR-0007**：push 须许可，merge 须授权；同账号 agent PR 无法获得 GitHub 正式 approval。
- **AGENTS 文档写回窗口**：PR 创建后、评审通过前写回；docs PR 的 squash 标题/正文取自 PR，而非分支提交。
- **仓库外记录不可引用**：GitHub 评论可编辑、可删除，仓库重建即消失（已发生两次），不能作为唯一账本。
- **ADR-0009**：CI 已有 title / attribution 校验，但只校验分支提交，不校验 PR 描述这一「squash 正文来源」。

## 提议

### 1. 评论 = 状态机消息，不是聊天

三套固定格式，首行是机器可读标记；正文中文。

**评审者：阻塞**

````text
REVIEW: BLOCKED · target <sha> · round <n>

## 阻塞
B1 `<file>:<line>` — <一句话问题>
- 证据：<文件行 / 命令输出 / 平台数据>
- 要求：<可验证的修正>

## 非阻塞
N1 `<file>:<line>` — <一句话建议>
- 证据：
- 可延后：是 / 否

## 已核验
- 形状：单提交 / diff 单意图
- 元数据：标题 / 描述 / trailer / 分支方向
- CI：required 全绿；skipped 符合上下文
- 事实：<抽查项>

## 结论
BLOCKED — B1/B2 关闭前不合入。
````

**作者：修正完成**

````text
REVIEW-FIX · target <sha>
| ID | 状态 | 落点 |
| B1 | fixed | `<file>:<line>` |
| B2 | fixed | `<file>:<line>` |
| N1 | deferred | <后续 PR / 理由> |
待复核。
````

**评审者：通过**

````text
REVIEW: PASS · target <sha>
closed: B1 B2 N1
verified: CI green · title/body synced · single commit · no open blocking
merge: squash
````

约定：

- `REVIEW:` 只由评审者发，`REVIEW-FIX:` 只由作者发；一条评论承载一个状态，不在评论区聊天。
- 行内评论只用于定位，所有结论必须回到汇总评论；汇总评论是唯一评审入口。
- ID 跨轮稳定：`B` = 阻塞，`N` = 非阻塞，`Q` = 提问；修正后状态只有 `fixed` / `deferred` / `rejected`。
- **每条阻塞项必须有证据**（文件行 / 命令输出 / 平台数据）；没有证据的只能算 `Q`，不能算阻塞。
- `PASS` 后不再提新问题；除非是修正本身引入的回归——那要写明「上一轮为什么没抓到」，并记为本协议的失败样本。

### 2. 一次评审跑完整清单

评审者在发 `BLOCKED` / `PASS` 前必须跑完下表；不允许「先报两条，等作者改了再发现第三条」。

| # | 检查 | 方法 |
| --- | --- | --- |
| 1 | 形状 | base/head、提交数（docs 恰好 1）、diff 是否单意图、有无无关文件 |
| 2 | 落地物元数据 | PR 标题（squash 主题）、PR 描述（squash 正文）、末尾 trailer、分支方向 |
| 3 | CI | required 全绿；skipped 是否符合触发上下文（docs-only / push） |
| 4 | 事实 | 日期、编号、PR 号、链接、命令、数字逐条对仓库或平台数据；「真实先例」必须在仓库里存在 |
| 5 | 规则一致性 | AGENTS / README / ADR / spec 对表；guides 不得新增规则 |
| 6 | 回归 | 修正 diff 是否引入新表述、新数字、新先例；上一轮 ID 是否全关 |
| 7 | 合并闸口 | 标题/描述已同步、单提交、trailer、CI、无 open blocking |

第 2 项与第 6 项就是 PR #13 第三轮与第二轮漏掉的两类；写进清单后，同类问题第一轮就能挡住。

### 3. 两轮收敛，第三轮必须拆或升级

```text
draft ──作者自检──→ ready
                      │
                      ▼
              REVIEW: BLOCKED ──作者一次修完──→ REVIEW-FIX
                      │                         │
                      │                         ▼
                      └──────────────→ REVIEW: PASS ──→ squash merge
```

- **第一轮**：完整清单，一次发全；没有 blocking 就直接 `PASS`。
- **作者修正**：一次 amend / push 修完全部 ID；PR 描述中的「评审修正记录」表同步更新。
- **第二轮**：只验闭环 + 回归 + 元数据；通过即 `PASS`。
- **两轮上限**：第二轮仍 blocked，禁止开第三轮；拆 PR、缩范围或升级给人决策，并记录原因。
- **时间盒**：单个 PR 评审从 ready 到 PASS 超过 2 轮或 24 小时，触发同上。

### 4. 角色、写回与授权

- **作者**：请求评审前自检（下面第 5 节）；修完全部 B 后发 `REVIEW-FIX`；维护 PR 描述中的评审修正表。
- **评审者**：跑完整清单、发一条状态评论、复核、在授权范围内合并；**不进入作者分支改代码**。
- **PR 描述是唯一评审账本**：作者写「评审修正记录」表（ID → 状态 → 落点），评审者在「评审结论」节写最终结论；评论只做通知。
- **落地物**：docs PR 的标题/描述随 squash 进入 dev 账本；代码 PR 的描述不进入提交，凡影响验收/规则的结论按沉淀三问落 journal / spec，普通评审留在 PR 描述。
- **评论不是审批**：`REVIEW: PASS` 是评审结论，不是 GitHub approval；合并授权仍按 ADR-0007。同账号自审的合法路径 = `COMMENTED` 评审 + PR 描述结论 + 人类明确合并授权，三者齐全，且不得暗示已获正式 approval。

### 5. 交流步数预算

目标：人类只在三个节点出现——**开工授权、升级决策、合并汇报**。

- **作者自检前置**：PR 模板增加「自检」节——标题 = 落地主题、描述末尾 trailer、docs 单提交、清单已跑；机械问题不进评审。
- **一次批量授权**：任务开工时一次问清 auto-commit / auto-push / 评审修正的 force push / docs PR `PASS` 后直接 squash 合入；之后不再逐次请示。
- **agent 间用 PR 交接**：`REVIEW:` ↔ `REVIEW-FIX:` 是消息，不是给人看的汇报；人类不需要转述内容，只在需要决策时被点名。
- **汇报粒度**：`BLOCKED` 只在需要人类拍板时上报；`PASS+merged` 合并后一条；中间状态不刷屏。
- **可选自动化**：CI 增 `pr-meta` job——docs/* 恰好一个提交、PR 描述末尾 trailer 合法；这能挡住「描述没同步」类问题。它改门禁矩阵，属 ADR-0009 范围，拟另登记为 `proposals/ci-gate-optimizations.md` 的 C6 候选（尚未建行），不塞进本协议。
- **度量**：每 PR 记录评审轮次、状态评论数、ready→merge 墙钟；目标 ≤2 轮、≤3 条状态评论（BLOCKED / FIX / PASS）。

## 毕业条件

- **试点**：接下来至少 3 个 PR（docs 与代码各至少 1 个）按本协议跑，平均 ≤2 轮，且无「元数据漏检 / 修正回归」类返工；人类确认授权模型可执行。
- **毕业产物**：AGENTS 提交纪律节新增「评审协议」子节；新增 `docs/guides/review.md`（清单 + 三套模板 + 常见误判）；`.github/PULL_REQUEST_TEMPLATE.md` 增加「自检」「评审结论」两节。
- **授权变更**：若把「评审修正 force push」或「docs PR PASS 后自动合并」纳入任务级授权，须先改 ADR-0007（正文不可变，走部分取代或新 ADR）；否则本协议只做流程约束，不动授权。
- **失败条件**：试点期内出现两次第三轮，或评审者仍靠临场发挥，则退回重写，不毕业。

## 被否方案

- **再开一个 GitHub 账号做正式 approval**：解决的是平台状态，不是评审质量；账号管理、凭据与「agent 归属」成本高于收益，Phase 0 不做。
- **把评论当审批**：评论可编辑、可删除、仓库重建即消失，且与 ADR-0007 的授权语义冲突。
- **一开始就自动合并**：协议未试点，自动合并会把评审失败直接变成 dev 事故；先人工 merge，数据够了再谈。
- **用 label 替代评论状态**：同账号下 label 与评论一样是平台状态，且更难看历史；暂缓，等有脚本消费者再评估。
- **评论首行加 JSON schema**：当前没有解析消费者，先用手写标记；等 `pr-meta` 或看板脚本出现再加。
