# Phase 0 的三条工程判据：账本、门禁、工具债

## 撞到了什么

- merge.sh 的 P0 设计在 proposal #30 就定了，但 SPEC-0001 的任务表止于 t6；Phase 0 的 #45–#49
  仍是手动快照合并，直到 #50 才用 `task merge` 自合并。**硬保证没有任务号，就会被「最后一个
  代码任务」挤掉**。
- A10 前置 PR 要「逐条勾选 + status done」，但 A10 自身包含 dev→main 与 tag；前置 PR 不可能
  包含执行后的证据。留空则 main 快照缺项，勾上则是提前声明——最后只能把「机械执行」写进
  journal。
- 工作树的 lefthook 不在 PATH，本地 commit 钩子实际没跑；沙箱 pnpm store 只读，`task ci` 也
  跑不了。**「本地验证过」这句话，可能只是「我以为钩子跑了」**。
- 收口后新增的文档（复盘 / pilot 记账）只落在 dev；main 的 v0.1.0 快照不会自动获得回填。
  #49（A5 ④）与 A10 受限例外是收口前合入的，已在 main。

## 搞懂了什么

- **账本判据**：PASS 冻结的是 title + body 快照，不是「评审过」这个感觉；写回窗口在评审通过前
  关闭；main 的收口快照只有一个落点（前置 PR），执行后才知道的证据必须在设计收口流程时就决定
  它怎么进 main。受限/例外要写进变更记录，不能靠「全勾」暗示全部独立验证完成。
- **门禁判据**：`ci-ok` 只说明 head 的 CI 矩阵过了，不等于 PASS，也不等于可合；PASS 是评论层的
  声明，快照脚本是合并时点的同步校验。docs 的 squash 正文来自 PR 描述，描述是落地物，不是说明
  文字；code 的 merge 正文为空，过程史在分支里。
- **工具债判据**：手动流程是兜底，不是排期。P0 硬保证应在 Phase 任务表里占一行；落地后要测
  「合并后核验」这条真实路径，而不只是 fixture/dry-run。工具吃狗粮（#50 自合并）比再写一篇
  设计文档更能暴露问题。

## 下次怎么用

Phase 1 开工前/收口前各过一遍：

- [ ] P0 工具是否在任务表里有任务号？没有就现在补，不靠「以后再说」。
- [ ] 收口前置 PR 是否包含所有**能进 main** 的最终账？执行后才知道的结果，是否已有明确落点？
- [ ] 这次合并是否用 `task merge`？若用手动流程，PASS target/hash 与落地 subject/body 是否逐项核过？
- [ ] PASS 后 PR 标题/描述是否冻结？描述里有没有「未来完成时」的措辞？
- [ ] 本地钩子/CI 是否真的跑了？没跑就写清原因，用 PR CI 做等价面，不假装本地全绿。
- [ ] 例外是否入账？A5 ③、A10 外部 clone、敏感数据演练这类「未完成」是否仍挂在账上？
- [ ] docs 回填是否只落在 dev？如果是，明确 main 快照会落后，并在下一次收口前置 PR 收口。

一句话：**账本先行、门禁分层、工具债按期还；手动兜底可以救急，不能当制度。**
