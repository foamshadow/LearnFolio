# pi -p 评审调用无 HTTP 超时：三次挂死、外层 timeout 兜底

> agent 起草、人审定（作者键 = 审定者）。本篇关联 PR #46。t6 的 commit 级评审（Reviewed-by，
> 语义见 ADR-0011）由 Claude Code 会话经 pi CLI 非交互模式（`pi -p -c`）调
> GLM-5.3 执行，会话跨 commit 续接（人类决策：复用评审员上下文，不每次重开）。
> 本篇记录该链路当日的三次挂死、判定方法与向前生效的使用纪律。

## 事件

t6 任务日（2026-11-18）四个提交的评审中三次单请求挂死：

- 第 2 提交（compose + env + Taskfile）评审首次调用：约 17 分钟无返回，
  转后台后仍挂；kill 后重试，约 3 分钟返回，结论 PASS。
- 第 3 提交（onboarding）评审调用：约 27 分钟无返回；kill 后带
  `timeout 480` 包装重试，约 2 分钟返回，结论 BLOCKED（内容有效）。
- 第 4 提交（journal 自身）评审首调：约 8 分钟无返回，被外层
  `timeout 480` 按预期杀掉（退出码 124）——兜底纪律首次生效；`-c`
  重试约 2 分钟返回，结论 PASS。

同会话（约 138KB 上下文）在第 2 提交重试时正常返回，排除服务整体故障与
上下文超限——判定为单请求 unlucky（连接挂起），pi 客户端对此无保护
（`-p` 模式没有请求级超时，挂起即永久等待）。

## 诊断

判定"挂"而非"慢"的依据：进程 CPU 0%（在等网络而非推理）；pi 会话文件
双采样 8 秒 mtime / size 零增长（`-p` 的 stdout 在最后才写出，中间态只能
看会话文件）。两条同时满足即 kill 重试，不再等待。

## 纪律（向前生效）

- 所有 `pi -p` 评审调用统一外层 `timeout` 包装；实测正常耗时 2~4 分钟，
  取 480s ≈ 2.6 倍余量。挂死属 pi 客户端行为，绕不过也无需改上游——
  外层兜底即可。
- 会话文件零写入数分钟 = 挂死信号；kill 后 `-c` 重试成本低：评审员上下文
  （此前的 BLOCKED 教训、前轮锚点）仍在会话里，"不重开会话"的原则不变。
- `timeout` 杀掉的调用不产生评审结论，不存在"半条 Reviewed-by"——trailer
  只在 PASS 后落盘，与 Reviewed-by 的重写语义（tree 变更即失效）天然相容。
