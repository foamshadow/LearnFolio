# 文档体系讲解：六类目录与规则生长

## 讲给谁 / 前置知识

给所有要在 `docs/` 目录里**写东西或找东西**的成员——无论你是第一次参加项目的新人，还是准备让 agent 替你干活的资深工程师。本文**不假设你懂任何文档工程知识**：全文每个术语第一次出现时都会就地解释；需要会的东西只有两样——会用文本编辑器，以及知道 git 的 add / commit / push 是做什么的（这三个词不熟的话，先找一份 git 入门教程把基础补齐，再来读 git-workflow.md——它假定你会基本操作，并不从零教 git）。

本文讲三层东西：**这个仓库有哪些文档、每类文档允许你怎么对待它、这些看似奇怪的规定各自在防什么事故**。规则的原文在 AGENTS.md 和 docs/README.md（它们是"法律条文"，本文是"教材"）。如果发现教材与条文冲突：以条文为准，并把冲突告诉我们——那会被当作教材的 bug 处理（这个机制在"真源层级"一节细讲）。

## 核心图景

### 一句话版本

**docs/ 里的每个文件按「允许被怎样修改」分进六个目录——你能不能改它、改了要走什么流程，由目录名决定，不由你的心情或职级决定。**

### 六个目录速查表

| 目录 | 它是什么 | 类比 | 你能怎么改 |
| --- | --- | --- | --- |
| `specs/` | 功能规格书——agent 开工前读的施工图 | 建筑图纸 | 受控：小修走文尾"变更记录"追加；方向变了开新编号取代旧文 |
| `adr/` | 选型决策记录——"当时为什么这么选" | 判决书 / 化石 | 正文一个字不改；推翻它的方式是写一份新的，并在两份之间互相登记 |
| `journal/` | 开发日志——一个事件一篇 | 航海日志 | 随便改：谁经历谁写，写错就改、有新进展就追加 |
| `learning/<作者键>/` | 学习笔记——被事故教育后的复盘 | 错题本 | 随便改 |
| `guides/` | 教学材料——本文就是一篇 | 教科书 | 随便改，但只能"解释规则"，不能"发明规则" |
| `proposals/` | 想法的孵化区——想法的第一落点 | 苗圃 | 成熟前随便改；文件名（slug）一旦定了不改 |

"受控 / 不可变 / 可变 / 可变偏受控"这四种变更语义的定义出自 ADR-0006——那篇是这套体系的设计决策记录，本文大量引用它。

### 内容的一生：一张流向图

```
想法 ──→ proposals（孵化区，随便改）──毕业评审通过──→ specs / adr（分配编号，进正式层）
                                                        │ 后来方向变了
                                                        ↓
                                                  新编号 ──supersedes──→ 旧编号（两份都保留）

讨论 / 复盘 ──→ journal（过程层：发生了什么）
结论蒸馏 ──→ guides / learning（教学层）
             两者分野：guides 是"我要学会 X"（主动建构），
             learning 是"X 撞了我"（事故驱动）
```

### 三个地基概念

后文会反复用到三个概念，先在这里讲透，后面就不再解释了。

**概念一：frontmatter（元数据头）**

随便打开一篇 spec 的开头，你会看到两行 `---` 之间夹着一段"键: 值"格式的文本。比如 SPEC-0001 的开头：

```yaml
---
id: SPEC-0001
title: "Phase 0：仓库骨架与工程化地基"
status: ready
author: foamshadow
date: 2026-11-12
tags: [infra, se-arch]
related: [ADR-0001, ADR-0002, ADR-0003]
---
```

这两行 `---` 之间的部分叫 **frontmatter**：用 YAML 写的文件元数据。YAML 是一种人可以直接读写的配置文本格式，规则极简——一行一个 `键: 值` 属性，方括号 `[a, b]` 表示列表。

为什么文档要带头部元数据？因为这个仓库的读者不只有人，还有**程序**：agent 靠它干活（比如"把所有 status 是 ready 的 spec 找出来"——这就是 agent 判断"哪些活可以开工"的机械方式），未来的展示网站也要靠它自动生成索引页。人对"颜色鲜艳的封面"敏感，机器对 `status: ready` 敏感——frontmatter 就是给机器看的封面。也正因如此，字段名和取值都是**闭合词表**（status 只允许固定几个词，完整词表见 docs/README.md）——写错词机器就检索不到，这不是格式洁癖，是数据质量问题。

**概念二：append-only（只追加，不重排）**

来自会计与审计领域的老原则：**账本上已发生的条目，只允许往下追加新条目，不允许改动已有条目的位置和编号**。银行流水是这个思想的日常版本——没有人会把上周的取款记录挪到这周，否则对账就乱了。

本体系把它用在两处：spec 的验收条目（编号 A1、A2、A3…只增不删、不换位置）和语义变更（只在文件尾部追加"变更记录"段落，不删旧内容）。为什么这么死板？下一节设计四有一个"静默指错"的完整演练——位置编号一旦重排，历史引用会悄悄指错而**全程没有任何报错**。计算机领域最危险的错误从来不是报错，而是静默。

**概念三：取代链（supersede chain）**

supersede 是"取代"。当一个决策被新决策推翻时，我们不用"编辑模式"改旧文档，而是"链表模式"：旧文档在自己的 frontmatter 里登记"我被谁取代了"（`superseded-by: 新编号`），新文档登记"我取代了谁"（`supersedes: 旧编号`）。一环扣一环，成为一条链。

写过链表或者看过 git 提交历史的人会发现是同一个思想：**每个节点只记录自己的直接前后关系，需要全貌时沿指针走**。收益是登记成本永远固定——每次取代只改两个文件各一行 frontmatter，不需要回头维护一张"全量对照表"；代价是查最新版要跳几步。用查询时间换登记成本，对这个规模的仓库是笔划算的买卖。

### 读 ADR 的正确姿势：按阶段读，不按编号顺刷

docs/README.md 里有一张「决策线」表，把全部 ADR 按阶段排好（本文写作时 13 篇）：选型（0001 / 0002）→ 流程设计（0003）→ 运行修正（0004 / 0005）→ 元决策（0006）→ 协作与继承（0007 / 0008）→ 交付（0009）→ 历史修复与评审记账（0010 / 0011）→ 远端重写与 journal 写回（0012 / 0013）。单看一篇 ADR 是碎片——比如 ADR-0005 讲"双合并策略"，但不知道 ADR-0003 就不知道它到底推翻了什么；按表从上往下读，才是这套规则一步步长成今天形态的完整故事。规则同时要求：新 ADR 合入时要在表里追加一行——所以这张表永远是最新的阅读入口，读 ADR 先看它。

## 为什么这样设计

八个设计点。每段的结构是：**规定是什么 → 它防的是什么事故 → 操作上怎么做**。完整论证与被否方案都在 ADR-0006，本文只点结论。

### 设计一：目录即变更语义

**规定**：六类文档、四种变更语义，目录名就是判据。

**防的事故**："这个文件我能不能直接改"变成需要问人的问题。文档一多、人一多，最常见的破坏不是恶意，而是善意地改错了地方——把 spec 的验收标准顺手"优化"了，把 ADR 的结论"更新"了。有了目录语义，人和 agent 都能在动手前机械自检：路径在 `specs/` 下？那语义不能直接动，走变更记录。

**操作**：动手前看一眼路径；不确定就回本文查速查表。

### 设计二：编号与冻结

**规定**：spec 与 ADR 有全局递增编号（SPEC-0001、ADR-0009…）。起草前先 `git fetch`（把远端的最新状态拉到本地），然后取现有最大编号 + 1——先 fetch 是因为你的本地目录可能落后，**远端才是登记簿**。评审通过（status 变 ready / accepted）的那一刻，编号与文件名**永久冻结、永不复用**。

**防的事故**：编号冲突与编号漂移。两个人同时起草都自称 SPEC-0005，合并时才发现撞号；或者一份 spec 从 0005 改号成 0006，所有引用它的地方悄悄作废。这与身份证号、学号是同构的设计——作废也不复用，因为"编号 → 含义"的映射一旦复用，所有历史记录都要重新人工核对。

**咬合规则**：**draft 状态的编号文档不得被引用**（要提就写标题，不写编号）。这不是孤立的洁癖，而是冻结机制的成本摊销：draft 期编号还可改，正因为没人引用 draft，改号才是零成本的。两条规则互相咬合，拆开哪条都不成立。

### 设计三：取代链与部分推翻

**规定**：方向变更 = 开新编号，新旧互登取代链（见地基概念三）；**部分推翻**用 `deprecated` 状态（不挂链），由新文档正文写明取代了旧文档的哪一部分。

**防的事故**："现行有效的规则到底是哪一版"无从判断。如果直接改旧 ADR 正文，三个月后没人说得清"这条规定是当初就有的还是后来改的"——ADR 的全部价值就在于保留"当时为什么这么决定"的完整语境（包括被否掉的方案：知道当初否了什么，才不会过两个月又提一遍）。

**真实先例**：ADR-0003（分支与合并）被 ADR-0005（双合并策略）部分推翻后，状态标的是 `deprecated` 而不是 `superseded`——因为 ADR-0003 的大部分条款还活着，只有合并方式条款死了；ADR-0005 的 frontmatter 写 `supersedes: ADR-0003`，正文写明取代范围。

**操作**：找一条规则的现行版本——沿 `superseded-by` 字段往后跳，跳到没有该字段的那篇就是现行（`superseded-by` 的含义是"取代我的人"，沿它走是往新方向）；反向考古才沿 `supersedes` 回溯，或者用 `git grep "supersedes.*ADR-0003"`（git grep = 在整个仓库的文件内容里按模式搜索，这条命令会列出所有声明取代了 ADR-0003 的文档）。

### 设计四：验收条目 append-only

**规定**：spec 的验收条目编号 A1、A2、A3…**只追加、不重排、不复用**；废弃的条目用删除线划掉、保留槽位；逻辑上属于中间位置的新条目也追加到末尾，逻辑顺序靠正文表达。

**防的事故**——来做一个"静默指错"演练，全程没有任何工具会报警：

1. 三月，某个 PR 的描述里写"本修复验证了 SPEC-0001-A3"，评审通过、合入。
2. 五月，有人觉得 A2 和 A3 顺序不对，把两条对调了一下——每个字都出于好意，git diff 干干净净。
3. 九月，新人读那个 PR，按编号去查 A3，看到的是**对调之后的另一条验收标准**。

链条上 git 完好、markdown 完好、编号格式完好——错的只有"含义"。append-only 让 A3 永远是 A3，历史引用才永远可靠。这也是它比"git 历史可以追溯"更强的原因：追溯需要人主动去查，而编号对齐在每次引用时自动发生。

### 设计五：proposals 毕业制

**规定**：想法的第一落点是 `proposals/`（不占编号，文件名即身份）；状态机是 idea → draft → review → adopted / rejected；毕业（adopted）= 毕业评审通过 + 分配正式编号，同时**正文替换成一句指针**（"已毕业为 X，真源以 X 为准"）；否决（rejected）的提案也保留——被否的理由本身就是知识。特例：roadmap 按 Phase 段落毕业，文内有显式声明。

**防的事故**：两个。其一，**半成品挤占正式层**——想法不经评审就进 specs，受控层会塞满没验证过的草稿，稀释施工图的信噪比，而且编号是永不复用的永久资源，给没想清楚的想法占号就是浪费。其二，**一份规则两份拷贝**——如果 proposals 毕业后正文还留着，agent 检索规则时会同时命中两份，"以哪份为准"又变成需要问人的问题；正文换指针后，真源永远唯一。

### 设计六：规则随第一个消费者到达

**规定**：AGENTS.md（规则真源）不预先写满——每条规则节恰好先于或伴随它的第一个消费者出现：验证命令节随 CI 骨架（t0）到达，Go 分层纪律随 Go 代码（t2）到达，提交钩子规则随钩子（t3）到达。

**防的事故**：没人遵守的完美规章。一条没有消费者的规则无从验证它是否正确、是否可执行，唯一的去向是过期后被整体遗忘——所以判据是"无消费者的规则无法验证"。这也解释了这套文档为什么**越早期越薄**：不是没写完，是还没到它的消费者出现的时候。如果你觉得"规则怎么这么少"，正确的反应不是补规则，而是问"它的消费者是谁"。

### 设计七：真源层级与维护触发器

**规定**：同一件事可能多处出现，优先级固定为 **AGENTS（做什么）> ADR（为什么）> guides（怎么理解）**；guides 只解释规则、不发明规则；冲突以 AGENTS 为准，冲突本身算 guides 的 bug，在同一 PR 里修正。配套的**维护触发器**：AGENTS / ADR 的改动若触及 guides 已覆盖的主题，必须在同一个 PR 里更新 guides。

2026-11-22 扩展（ADR-0013 / AGENTS「文档写回」节）：触发器的覆盖面不再只盯 AGENTS / ADR 的 PR——**实现与配置变更（ci.yml、merge.sh、钩子、脚本）同样触发复述面检查**（清单 1 第 2 项：grep 复述了该事实的文档，窗口内更新或记录"无需更新"）。动机是实测事故：C4 落地（#36/#40）改了 ci.yml 的 filters，不碰 AGENTS/ADR，原触发器永远不响，`ci-gate.md` 的 filters 复述静默过期直到 #62 补修。每任务执行载体 = PR 描述的写回自查区（清单 1 五项，见 AGENTS「文档写回与收口清单」节）。

**防的事故**：过期教材。过期教材比没有教材更危险——读者会拿着错误的心智模型自信地干活。触发器把"改了规则记得同步教材"从个人美德变成流程义务（类比软件工程里"改了代码必须同步改测试"）；真源层级则保证冲突有唯一裁决，不会陷入"两份文档打架、各自都有人信"的僵局。

### 设计八：流程冻结线

**规定**：Phase 0 收口（打上 v0.1.0 标签）之前，规则允许快速迭代——这个仓库真的删库重建过**两次**：第一次起因是首提交漏了 agent 署名（journal 2026-11-13 篇）；第二次是 squash 合并规则定型后，把早期 docs 变更留下的 merge 节点线性化，让历史形状与规则一致（journal 2026-11-14 篇「二次重建」）。第二次的存证至今可查：现仓库创建于 11-14 19:50（CST），PR #1–#7（分支名 docs/replay-1 至 replay-7）在其后约两分钟内（19:51:44–19:52:48）秒开秒合、与 dev 第一父链上七条 squash 提交主题逐一吻合——那是重建后对账本的补录。两次重建的窗口前提相同：**零协作者、零 clone**。收口之后规则进入基线，任何变更只走 ADR 取代链 + PR，**不重写已发布的历史**——重建的机会窗口关闭后不再重开，这正是冻结线最强的论据。

**防的事故**：仓库历史不可信。前期激进修订在"零协作者、零 clone"时是廉价的重置机会，错过窗口再改写历史，就要向所有已克隆仓库的人解释。冻结线是"快速试错"与"变更控制"的分界碑。本文写作时仓库仍在冻结线之前——所以你现在读到的规则还会演进，而本文（按维护触发器）也会跟着改。

## 常见误区

每条按"误区场景 → 为什么错 → 正确姿势"展开。

1. **"guides 写得最详细，我以它为准"**
   真源方向反了（见设计七）。**正确姿势**：把 guides 当课程、把 AGENTS 当法条；发现不一致时按 AGENTS 行事，同时报一个教材 bug。

2. **"某份 spec 还是 draft，但内容肯定不会变了，引用一下没关系"**
   破坏了设计二里互相咬合的机制——draft 不可引用正是"改号零成本"的前提。**正确姿势**：提标题不提编号；等它 status 变 ready 再引用编号。

3. **"这个 ADR 结论过时了，我直接把正文改掉"**
   ADR 正文不可变。**正确姿势**：写新 ADR，旧 ADR 挂 `superseded-by`（整体推翻）或标 `deprecated`（部分推翻），新 ADR 写 `supersedes` 和取代范围。

4. **"废弃的 spec 删掉吧，目录干净点"**
   目录即登记簿，删文件等于烧掉编号史。**正确姿势**：status 改 abandoned，文件留着。

5. **"有个新想法，直接起草 SPEC 才显得正式"**
   第一落点是 proposals（见设计五）。**正确姿势**：先孵化，毕业评审通过再拿编号；直接占号等于浪费一个永不复用的永久资源。

6. **"把验收标准改成 A2.5 插在中间更合理"**
   append-only 禁止重排（回看设计四的静默指错演练）。**正确姿势**：新条目追加到末尾，逻辑顺序在正文里表达。

7. **"编号取我本地目录里最大的 +1 就行"**
   本地目录可能落后于远端。**正确姿势**：起草前 `git fetch origin`，按远端取 max+1。

8. **"这篇外部设计文档讲得真好，我在 spec 里引用一下"**
   仓库自足原则：任何人 clone 本仓库后必须能独立施工，不依赖仓库外的任何记录。**正确姿势**：外部材料确需作为施工输入时，收进仓库。仓库里的真实先例：SPEC-0001 把 t0 / t2 的规则素材全文移进自己的附录（见其"变更记录"）；遗产裁剪类输入的来源账要求写在 SPEC-0001-A9。
