# agent 协作讲解：署名、授权与确认链

## 讲给谁 / 前置知识

给两类读者：**与 agent 协作干活的人类**（你要知道 agent 被允许做什么、什么必须经过你），以及**作为执行者的 agent**（你要知道自己的权限边界与告知义务）。前置：读过 git-workflow.md（提交、trailer、PR 流程已在那篇出现过，本文不重复细节）；知道 doc-system.md 的真源层级。不假设你懂"信任模型""授权体系"这类词——本篇全部就地讲。

规则原文：AGENTS「提交纪律」「破坏性操作」两节；决策出处：ADR-0004（署名）、ADR-0007（授权）、ADR-0008（继承）、ADR-0003（破坏性操作清单）；孵化中的升级提案：proposals/agent-confirmation-chain。本文与条文冲突以条文为准，并当教材 bug 报告。

## 核心图景

### 一句话版本

**本项目里 agent 是主要实现者，但 git 与 GitHub 只认识人类身份——三个机制把"agent 干的活"变成可查证、可授权、可升级的：署名记录谁参与，授权划定谁允许做什么，确认链把关不可逆操作。**

### 三个机制总览

| 机制 | 回答的问题 | 载体 | 状态 |
| --- | --- | --- | --- |
| **署名** | 这条提交是谁（哪个 agent / 哪个人）做的？ | `Assisted-by` trailer（提交正文末行） | ✅ 现行（ADR-0004） |
| **授权** | agent 允许自主做到哪一步？ | 双授权开关 + 操作分级 | ✅ 现行（ADR-0007） |
| **确认链** | 不可逆操作由谁确认才算数？ | 分级外部确认（L0–L3） | 🚧 孵化中（proposal） |

为什么需要它们？因为一个根本性的错位：**git 的两个身份字段（author 作者、committer 提交者）恒为人类**——GitHub 没有 agent 账号体系，agent 在平台的视野里不存在。如果不补机制，agent 干的活与人类写的在历史上无法区分：时间线没法按 agent 切分，出问题没法查证，规则缺失的错误不会被检出、只会被继承。这个洞真实漏过水：建仓首提交（20 件文档）因为没有任何 agent 署名，次日被发现后撤回重做——这是署名规则（ADR-0004）的直接触发事故（完整过程见 journal 2026-11-13 篇）。

### 地基概念一：声明 ≠ 证明（claim ≠ proof）

`Assisted-by: ZCode:glm-5.3-flash` 这行 trailer 的性质要拿捏准确：它是**参与者对来源的声明**，不是第三方核验过的证明。它的可信度来自两层保障——agent 按信源清单查证后才写（见"署名"一节）、人类评审时可抽查——但它**不得用于归责或能力认定**："这条提交是 GPT 写的所以肯定有 bug"是错误用法；正确用法是"这条提交声明由 GPT 辅助，评审时按抽查纪律对待"。一句话：**trailer 回答"谁参与了"，不回答"谁负责、谁更强"**。责任归属恒定：author 与 committer 是人类（审定者与执行者），规则没有转移责任给 agent，来源标签只做加法。

### 地基概念二：操作分级（五档）

agent 对仓库的每个动作，按风险分五档，档位决定"不经人类能走到哪一步"：

| 档 | 操作 | 人类参与形式 |
| --- | --- | --- |
| 自主 | 读、改工作区、查看 | 无——随时可做 |
| 告知 | 本地 commit（已获 auto-commit 时） | 事后知晓：改了什么 / 为什么 / 几个 |
| 逐条审批 | 未获 auto-commit 时的提交（`wip:` 例外） | 事前逐条确认 |
| 确认 | `docs/*` 提交 | 文件清单 + 关键点，点头才提交 |
| 许可 | push（未获 auto-push 时逐次）、合并 PR、打 tag、force push、`rebase -i`、`revert -m` | 明确授权该次操作 |

读表的钥匙是**风险差异**：commit 发生在本地，可撤可改，所以最低只需"告知"；push 把提交送出本地、进入他人视野与 CI，不可撤回，所以默认要许可（除非授予 auto-push）；`docs/*` 提交最特殊——它没有 PR 前的 rebase 整理机会（恰好一个提交、squash 即落地），**提交即定稿**：事后只能 amend + force push（需人类确认），没有轻量改写的兜底，所以始终要确认、不受 auto-commit 影响。这个分级是 ADR-0007 的核心，下一节展开。

### 地基概念三：WIP 文化与可编译阶梯

协作里"提交"不等于"交付"。开发期的提交是**草稿**（`wip:` 前缀），草稿免审、允许不编译——但提交仍须告知；整理后（PR 前）保留的提交必须是完整逻辑单元且**可编译**；合入 dev / main 必须全绿（CI 保证）。四级阶梯：

```
WIP 草稿        不要求可编译，可推送（任务分支不跑 CI）
   ↓ 收敛
锚点            一个可验证步骤，应编译过 / 测试绿
   ↓ 整理
逻辑级提交      必须可编译（bisect 可用）
   ↓ PR
合入 dev/main   必须全绿（CI 门禁）
```

这个阶梯解决了"每个提交都可编译"与"WIP 草稿"的直接冲突：不同阶段不同要求，谁也不用把工作藏在工作区里。

## 为什么这样设计

### 设计一：署名——opt-out 的 Assisted-by trailer（ADR-0004）

**规定**：每条提交携带 `Assisted-by: <harness>:<model>` trailer（如 `Assisted-by: ZCode:glm-5.3-flash`）；纯人类提交写 `Assisted-by: none`；**缺席即违规**。harness 与 model 键在 AGENTS 提交纪律节**闭合登记**——新值必须"加一行 + PR"，不能现场发明。

**防的事故**：三个，按严重程度排。

其一，**规则缺失则错误不被发现**：没有署名规则，"哪些提交有 agent 参与"在历史里不可判定——错误不会被检出，只会被下一代提交继承。其二，**opt-in 模式的结构性漏洞**：如果规则是"agent 参与时才写"（opt-in），CI 只能校验"写了的格式对不对"，校验不了"该写而没写"——漏写在机制上不可检测。opt-out（缺席即违规）让"每条提交都该有一行"成为可校验的断言。首提交事故正是这个洞：没人恶意漏写，但没有任何机制能发现它漏了。其三，**自由文本不可聚合**：像"本提交由 AI 辅助"这类自然语言标注无法被机器切分统计，时间线页（本项目的产品功能之一）就无法按 agent 维度展示。

**键怎么填**：trailer 的值必须来自**查证**，不是自报——查证顺序固定为：harness 的 model 配置 → 系统提示中的 model id → 自省命令；精确不到版本粒度就**问人，不猜**。键名大小写敏感、值 ASCII 无空格，完整键表见 AGENTS（当前：harness 有 DSH / ClaudeCode / ZCode；model 有 deepseek-v4.1-flash-1017 / glm-5.3-flash 等，以表为准）。多参与方各写一行、行序即参与顺序、不表达权重；**冲突解决者**在解决冲突的提交上追加自己一行。

**两个结构性例外**：merge commit 不携带 trailer——平台生成的合并提交不注入内容，结构上无法携带（所以署名校验只看非 merge 提交）；squash 落地的提交不例外——它的 trailer 来自 PR 描述末尾的占位行（git-workflow.md 第 4 步讲过的通路），漏填即被 attribution job 判红。

**被否方案里最值得记住的两个**（完整表在 ADR-0004）：`Co-authored-by:` 被否——GitHub 会尝试把它关联到账号，而 agent 没有账号，且语义上把 agent 抬成"共同作者"，与"agent 起草、人审定"的定位不符；环境变量注入（`LF_HARNESS` / `LF_MODEL`）被否——多 harness × 多 model 的环境里 shell 全局变量必然错配，配置负担随模型数线性增长。

### 设计二：授权——双开关 + 操作分级（ADR-0007）

**规定**：任务启动时一次性申请两项**独立**授权——

- **auto-commit**：授予后，提交前告知即可，不必等逐条确认；未授予则逐条审批（`wip:` 除外）；
- **auto-push**：授予后，任务内所有 push 免逐次审批，但**每次 push 后必须报告**；未授予则每次单独请示。

两项都是**任务级**：任务结束自动失效，可随时撤销。加上地基概念二的五档分级，构成完整的授权面。

**为什么拆成两个开关**：因为 commit 与 push 的可逆性不同。commit 在本地，错了可以 `git commit --amend` 甚至 reset，成本近零；push 把提交送出本地——进入队友视野、触发 CI、可能被他人基于它工作，**事实上不可撤回**。合并成一个"自主权"开关，要么 agent 被 push 拖累（每推一次等一次），要么 push 被豁免（静默外发）。分立后可各自授予：常见组合是"给 auto-commit 不给 auto-push"——agent 高吞吐写，推送节奏由人控制。

**为什么默认 push 要许可**：被否方案表里的对照是"push 全自主"被否——理由一句话：**发布不可逆，许可成本低于误推成本**。翻转条件也预登记了：出现只读镜像等安全机制时可以重议。

**告知义务的内容**：所有提交前说明三件事——**改了什么、为什么、涉及几个提交**。注意 auto-commit 省的是"等待确认"，不省"告知"：静默连提多个提交是被明确禁止的行为——不能让开发者只能靠事后翻历史才知道发生了什么。`wip:` 免审但同样要告知。

**docs 提交为什么始终要确认**：这是分级表里唯一高于"告知"的常设档。因为 `docs/*` 分支恰好一个提交、squash 即落地——**没有 PR 前的 rebase 整理机会**，提交即定稿：事后改写只能 amend + force push（需人类确认），成本远高于提交前确认。注意它仍走 PR 评审、CI 与分支保护，门禁一项不少；要确认的是"内容"，因为事后重写的通道太窄。确认的形式：给出文件清单 + 关键改动点，取得同意后再提交。

**无人在场怎么办**：agent 重启 / 恢复后发现任务中断，默认行为是——本地做 WIP 提交、**不推送**，恢复后向人报告，并补申请两项授权。缺省方向永远是保守侧。

### 设计三：这些规则从哪来——继承与裁剪（ADR-0008）

协作规则的相当一部分不是凭空发明，而是从前序项目**继承并裁剪**而来（harmony-wechat 与 foampray）。判据三条**全部通过**才继承：工具无关（不绑定特定技术栈）、对 5 人团队成立（不是临时约定）、有消费者（现在或最近一个任务用得上——没有消费者不预支）。处置分三类：直接继承（语义不变）、改写继承（按本仓库的 PR 门禁改写——例如前项目"commit 即评审点"建立在无 PR 门禁的前提上，照搬会与 auto-commit 冲突）、不取（工具特定 / 课程语境 / 无消费者）。每条继承条款在 AGENTS 里注明来源（H § = harmony，F § = foampray）。

对协作最关键的一条继承是**事故→制度闭环**：事故当天或最近一次 PR 内，journal 记事故 + 落一条带判据的条款 + 关联 PR——你读过的"首提交缺署名 → ADR-0004"正是这条条款落档前的一次完整闭环先例：先有事实，后有条款。它保证本篇教材的每个"防的事故"都有真实出处，而不是假想敌。

### 设计四：确认链——破坏性操作的分级确认（孵化中）

**现状**：Phase 0 里，破坏性操作——`rebase -i` 整理门、force push、打 tag、dev→main 收口合并、`git revert -m`——全部由**人类**执行或确认（清单见 ADR-0003）。这是刻意的保守：agent 的确认机制还没建立，先把不可逆操作握在人类手里。

**孵化中的提案**（proposals/agent-confirmation-chain，状态 draft，**不是现行规则**）：把"必须人类"改写成"需要独立于执行者的确认"，并按破坏程度分级——L0 agent 自主（commit、非 force push）；L1 上一层确认（整理门、force push、revert -m）；L2 ≥2 个独立确认来源（打 tag、dev→main 收口）；L3 spec 评审归人类核心成员。关键的独立性定义写死了：**独立来源 = 异 harness / 异模型家族 / 人类，同源自审不算**（防止模型互相同意产生的回声室）。确认留痕进 PR 描述，审计链即账本。毕业条件有三：OpenRig 引入（Phase 1 评估）、Phase 1 收口作为首次全链 L2 演练通过、演练复盘无致命缺陷——在那之前，教材只预告它的存在，不按它执行。

### 实操速查（agent 视角的一页流程）

```
任务启动    说明任务内容 → 申请 auto-commit / auto-push（等答复）
开发中      提交前告知（改了什么 / 为什么 / 几个）
            trailer：按信源清单查证 → 写 Assisted-by: <harness>:<model>
            wip: 提交免审；锚点应编译过
推送        未获 auto-push → 逐次请示；已获 → 推完报告
docs 改动   文件清单 + 关键点 → 确认后才提交（auto-commit 不豁免）
冲突解决    解决者的提交上追加自己的 Assisted-by 行
整理/强推   人类执行（Phase 0）；自己不要动
中断恢复    本地 WIP、不推送、报告 + 补申请授权
任务收尾    双授权随之失效，不必"注销"
```

## 常见误区

每条按"场景 → 为什么错 → 正确姿势"展开。

- **"这次改动很小，trailer 就不写了"**
  opt-out 的全部意义就是"缺席不可检测"——放开任何一次例外，规则就退化为 opt-in，漏写重新变得不可见（首提交事故的成因）。**正确姿势**：每条提交都写，纯人类写 `none`，无例外。

- **"这条提交是 X 模型写的，质量肯定不行，打回"**
  trailer 是来源声明不是质量证明（地基概念一）。**正确姿势**：按评审抽查纪律对待，不按来源预判；归责与能力认定不基于 trailer。

- **"我们组新用了个 agent，我造个键：`Assisted-by: my-agent:latest`"**
  键表是闭合登记的——自造键让聚合与校验失效。**正确姿势**：新 harness / model = AGENTS 键表加一行 + PR；查证不到精确版本就问人。

- **"拿到 auto-commit 了，那我可以一口气静默提十个提交"**
  auto-commit 豁免的是"逐条等确认"，不豁免"告知"——静默连提是明确禁止的行为。**正确姿势**：提交前照常说三件事（改了什么 / 为什么 / 几个）。

- **"wip: 提交是草稿，告知也省了吧"**
  WIP 免的是**审**，不免**告知**——可见性要求对草稿同样成立。**正确姿势**：草稿提交照常说明。

- **"docs 改动我也拿到 auto-commit 了，直接提交"**
  `docs/*` 提交始终是"确认"档——它没有 rebase 兜底，提交即发布，auto-commit 对它无效。**正确姿势**：清单 + 关键点，等同意。

- **"rebase 解决冲突时，这个提交我大改了，还写原来的 trailer"**
  冲突解决者实质参与了内容成形。**正确姿势**：追加自己一行（`Assisted-by` 键可重复、各占一行、行序即参与顺序）。

- **"任务做到一半人不在了，那我把当前进度 push 上去，免得丢"**
  无人在场的缺省方向是保守：本地 WIP、不推送、恢复后报告并补申请授权。push 不可逆，"防丢"不能正当化越权外发。**正确姿势**：local commit only。
